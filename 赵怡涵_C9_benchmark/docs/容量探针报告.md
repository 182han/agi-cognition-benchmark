# 搜索预算容量探针报告

**问题**：本基准上最强的确定性归纳器 `search_solver` 在 dev 上拿 0.7857、holdout 上 0.7619，而给出真实规则的 `reference_oracle` 拿 1.0000。这个差距，是"搜索得不够狠"，还是"问题结构决定的"？

**结论（先给）**：不是搜索预算问题。把搜索宽度放大 3.75 倍、把假设语言放大到允许更长规则，dev 分数一分没动，holdout 反而最多掉到 0.7500。**差距 100% 集中在「不给示例」的阶段（Phase A），而该阶段归纳器无示例可归纳、只能照抄输入**——这是结构性上限，不是算力上限。

---

## 1. 探针设计

只动两个"思考预算"旋钮，其余一律不动：

| 探针 | 搜索宽度 beam | 规则最大长度 max_len | 相对正式配置 |
|---|---|---|---|
| 正式 `search_solver` | 160 | 2 | 基线 |
| P1 | **600** | 2 | 同一条假设语言，只是搜得更宽（3.75×） |
| P2 | 160 | **3** | 假设语言变大，允许更长的规则 |

**不变量（探针全程未改）**：

- 题面、示例、金标答案：完全未改，`data/` 与 `keys/` 内容哈希与冻结快照一致。
- 评分器、阶段划分、题目数（84/分片）：完全未改。
- 阶段权重（Phase A 24 / B 36 / C 24）：完全未改。

**为什么必须先备份再跑**：`run_eval.py` 的输出文件名由适配器名决定，探针会写成 `search_solver_*` 并**覆盖正式结果**。脚本 `scripts/probe_capacity.sh` 因此先把正式结果备份到 `/tmp/c2a_official`，跑完立即复原，之后追加一次冻结校验。

**复现命令**：

```bash
cd 赵怡涵_C9_benchmark
bash scripts/probe_capacity.sh > results/probe/probe_capacity.log 2>&1
```

## 2. 结果

| 运行 | 分片 | 总体准确率 | Phase A（24，不给示例） | Phase B（36，给示例） | Phase C（24，二次反馈） |
|---|---|---|---|---|---|
| 正式 `search_solver` | dev | **0.7857** | 0.2500 | 1.0000 | 1.0000 |
| 正式 `search_solver` | holdout | **0.7619** | 0.1667 | 1.0000 | 1.0000 |
| P1（beam 600） | dev | 0.7857 | 0.2500 | 1.0000 | 1.0000 |
| P1（beam 600） | holdout | **0.7500** | 0.1667 | 1.0000 | 0.9583 |
| P2（max_len 3） | dev | 0.7857 | 0.2500 | 1.0000 | 1.0000 |
| P2（max_len 3） | holdout | **0.7619** | 0.1667 | 1.0000 | 1.0000 |
| 参考上界 `reference_oracle` | dev / holdout | 1.0000 | 1.0000 | 1.0000 | 1.0000 |

四项探针运行全部 `exit=0`，无解析失败（`parse_failure_rate=0.0`），耗时 23.4–52.8 秒/分片。

**读法**：

1. **加宽度没用**：beam 160 → 600，dev 一模一样 0.7857；holdout 从 0.7619 掉到 0.7500（Phase C 丢了 1 题），是噪声级波动，方向上无收益。
2. **加语言也没用**：允许 3 条规则长度的假设（max_len=3）后，两分片与正式结果**逐题一致**（dev 0.7857、holdout 0.7619，Phase A/B/C 分解全同）。说明当前失败不是"正确答案长在假设空间外"。
3. 唯一变化的是 Phase A 永远不动：dev 恒 0.2500、holdout 恒 0.1667。两个旋钮都碰不到它。

## 3. 差距的算术：全部缺口都在 Phase A

把总体准确率按阶段拆开算，缺口可以精确对上：

- **dev**：差距 = 1 − 0.7857 = 0.2143 = **18/84**；而 Phase A 丢的题数 = 24 × (1 − 0.2500) = **18**。两个数相等。
- **holdout**：差距 = 1 − 0.7619 = 0.2381 = **20/84**；Phase A 丢的题数 = 24 × (1 − 0.1667) = **20**。两个数相等。

也就是说：**Phase B 与 Phase C 已经满分（1.0000），全部缺口由 Phase A 单独贡献。** 这不是巧合，而是因为 Phase A 是"不给示例"的阶段——归纳器没有任何样本可以归纳，只能退化为照抄输入。证据就在分数文件里：

```
copy_input_rate_phase_A = 1.0     （dev 与 holdout、正式与探针，全部为 1.0）
copy_input_rate_phase_B = 0.0556 / 0.3056
acc_phase_A             = 0.2500 / 0.1667
```

`copy_input_rate_phase_A = 1.0` 意味着 Phase A 的每一条回答都是原样复制输入。一个靠示例做规则归纳的解题器，在零示例条件下没有可搜索的目标，所以**搜索宽度和假设语言都救不了它**——这正是探针实测出来的结果。

而 `reference_oracle` 在 Phase A 也是 1.0000，只因为它**直接知道真实规则**，不需要归纳。这恰好划清了两个概念：

- 0.7857 / 0.7619 不是"这个基准对搜索来说太难"，而是"**零示例条件下的归纳** 是这个题目里未被任何非先知解法拿下的部分"。
- 因此这个分数是有意义的能力刻度，不是评测配置不足的产物。

## 4. 对评审意见的回应

评审指出"缺少前沿模型基线、缺少人类基线、缺少 Kaggle 官方榜成绩"。本探针不替代这些缺口，但补上了另一类证据：**用受控实验证明本地分数上界的瓶颈位置**。

- 它回答了"是不是你的解题器太弱/搜得不够"这一质疑：不是，预算翻倍无收益。
- 它给出了本地分数与理论满分之间的差距来源，并且给出了可复核的算术（18/84、20/84）。
- 它不改题、不改分、不改数据，事后冻结校验仍然通过，任何人都能重跑得到同样数字。

**仍然缺的**（如实列出，不粉饰）：

| 缺口 | 状态 | 说明 |
|---|---|---|
| 前沿模型基线 | 未做 | 本包只有本地 4B 级小模型（qwen3-4b、gemma4-e2b，量化），**没有任何前沿模型分数**，排行榜里也不冒充 |
| 人类基线 | 未做 | 需要真实人类受试者按同一协议答题，本轮未执行 |
| Kaggle 官方榜 | 未提交 | 无官方榜成绩，不虚构 |
| 一次小模型评测 | 已作废 | `deepseek-v4-flash` 的 holdout 结果（tasks 0.798）因评测结束后题目被重新生成而作废，已从排名中剔除，单独存放、不参与比较 |
